# ADR-0066: Install shell completions alongside pages

Status: Accepted
Date: 2026-10-13

## Context

maniac exists because uv, pipx, cargo, go, npm and mise install a tool's binary and nothing else: no page where `man` looks.
The same installers leave out shell completions, which Homebrew and distribution packages set up.
Completions face maniac's discovery problem unchanged: which binary the login shell runs, who installed it, at what version, and whether its own files can be reached; the four rules of `docs/CONTRACT.md` answer them the same way.
The installation surface differs: one convention per shell, and zsh has no user directory it reads by default.

The user decided: completions are installed by default; the shell is the login shell's (`$SHELL`), and an explicit shell can be named.

## Decision

`install` installs a tool's completions with its page, for the login shell, unless `--no-completions`.
They go with the page: a tool that ends up with no page (refused, or `--no-generate` with nothing shipped or upstream) gets no completions either, so `list`, `update` and `remove`, which work page by page, account for every completion maniac installed.
`--shell bash|zsh|fish` (repeatable) names the shells instead; the shells a tool's completions were installed for are recorded, and `update` keeps to them.

A completion comes from the first of:

- **shipped**: a completion file the tool installed in its install root (a release archive's `completions/` or `autocomplete/`, a `share/bash-completion`, `share/zsh/site-functions` or `share/fish/vendor_completions.d` tree), proven inside the root like a shipped page;
- **generated by the tool**: the tool's own generator, found in the `--help` it already crawls (`completion <shell>`, `completions <shell>`, `generate-shell-completion <shell>`, `--generate-shell-completion <shell>`, `--show-completion <shell>`), run by its resolved path from `$HOME`; its output is accepted only when it looks like a completion script for that shell.

Never generated by a model: a completion script is code the shell runs, so a wrong one is not a stale paragraph.
A tool with neither has no completions, and `why` says so.

Each completion is a symbolic link in the shell's user directory, as pages are:

| Shell | Link | Loaded |
|---|---|---|
| bash | `~/.local/share/bash-completion/completions/<tool>` | by bash-completion, on first use |
| zsh | `~/.local/share/zsh/site-functions/_<tool>` | from `$fpath`, which must include that directory |
| fish | `~/.local/share/fish/vendor_completions.d/<tool>.fish` | by fish, on first use |

A shipped completion links to the provider's file, so an upgrade in place refreshes it; a generated one links to maniac's copy under its data directory, rewritten by `update` when the tool's version changes.
maniac never edits a shell's startup files (rule 1): when zsh's `$fpath` lacks the directory, `install` and `why` print the line to add.

Completions are recorded in the manifest, in a `completions` section keyed by tool and shell, with the same ownership rules as pages: maniac removes only what it recorded, and a file it did not install is reported and never replaced.
The schema version becomes 2; a version-1 manifest reads as having no completions.

`remove` removes a tool's completions with its page; `list` shows the shells each tool has completions for; `why` explains which source each shell's completion would come from.

## Consequences

`docs/CONTRACT.md` names completions in its opening sentence, in rule 1 and rule 3, in a section on where a completion comes from, and in its commands.

Out of scope for now: completions for system packages' tools (their package ships them, as it ships their page); shells other than bash, zsh and fish; recovering completion records from links when the manifest is damaged (pages recover; completions are reinstalled by naming the tool); `scan` reporting completions.

## Corrections

2026-10-13: completions gain the `upstream` source pages have, between shipped and generated, at the user's request.
A cargo or go install is a bare binary: the completions its project keeps (eza's `completions/zsh/_eza`, fd's `contrib/completion/_fd`) were left unused.
As for pages, only the tag matching the installed version is asked (ADR-0016), so a completion never offers another version's flags: the repository tree at that tag, then the GitHub release's assets named as a completion file.
Release archives are not unpacked: the platform tarballs that carry completions are megabytes each, and a tool shipping one usually has a generator too.
A check that did not complete falls through to the generator, and `why` says so when nothing answered (rule 4).
`fd --gen-completions` joins the generator forms the help is searched for.

2026-10-13, later: completions are found by name, as the user's own dotfiles discovery finds them (`find -name`, a tree listing at the tag), rather than in a fixed list of directories.
An install root and a repository tree at the tag are both searched for the tool's completion names, plus the generic `completion.<shell>` (aichat, herdr) and `tool.zsh`; at most six levels deep, never in test fixtures, vendored trees or a virtualenv's packages.
Two different files that each read as the completion are ambiguous and neither is taken (rule 4), as the dotfiles discovery skips an ambiguous destination; copies of one file are one completion.
`why` names the ambiguity when no later source answers.

2026-10-13, last: a fourth source, `derived`, after the tool's generator, at the user's suggestion: fish already generates completions from man pages.
What derives it is the shell's own parser, never a model nor maniac's own: for fish, `create_manpage_completions.py` from the installed fish, run on the page maniac installed alone (never `fish_update_completions`, which rewrites fish's cache for every page on the machine); for zsh, a `_tool` that calls `_gnu_generic`, and for bash one that calls bash-completion's `_longopt`, both of which read the tool's `--help` live when the shell completes.
zsh and bash get one only when the crawled `--help` lists a `--long` option; otherwise the shell's default beats a completion that offers nothing.
A fish completion derived from a generated page inherits that page's mistakes; it is regenerated whenever `update` reinstalls the page.
`argc --argc-completions` is not a generator for argc itself (it completes argc-based scripts) and is not added.

2026-10-14: completion records are recovered from their links when the manifest is damaged, by the rules pages follow (ADR-0028), at the user's request.
Salvaged rows first, then the checkpoint's where the link still points at its recorded target, then a link that points at maniac's own copy under the name `install` writes it under; that copy is the only evidence, as `output_dir` is for a page.
A shipped completion links to the provider's file, which a hand-made link looks the same as, so it is not reconstructed: naming the tool to `install` again records it.
A reconstructed record has no version or generator arguments, which exist nowhere on disk.
An unrecorded link to maniac's own copy is adopted on every manifest write too, as an orphaned page link is: an install interrupted between linking and recording otherwise refused its own link next time.

2026-10-14, later: `scan` reports, for each tool, where `install` would take the login shell's completion from, at the user's request; the contract's `scan` row says so.
The answer is the same lookup `install` acts on, generator included: measured on twenty tools, reading each one's `--help` cost 0.1 to 2 seconds (the generator itself under 0.2), doubling a warm `scan` here, so each answer is cached per binary, keyed by the shell, the binary's name, the file that runs (path, size, modification time) and the installed version.
A new or upgraded tool pays once. An answer a check before it could not finish is never cached (rule 4): an upstream check that did not complete may have had a completion that comes first.
The column appears only for a login shell maniac installs completions for; every answer is about that shell.
The lookup moved from `orchestration` to `sources.lookup.completions`, beside the page source order, so `listing` can ask it.

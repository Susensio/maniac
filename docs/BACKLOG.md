# Backlog

Open work with no single line to mark. `rg -n 'BUG:|TODO:'` lists the rest.

- Define and implement upgradeable MANIAC-managed manpages. Record generation inputs, then compare the installed tool version and documentation context to identify pages that have become stale and can be regenerated.
- Resolve installed package metadata before Mise registry inference. For a resolved package-manager installation, parse the package manifest for repository, homepage, executable, and version metadata; support npm `package.json` first (an existing gap: `bash-language-server`, installed via `~/.config/mise/conf.d/lsp.toml`, has a `package.json` naming `https://github.com/bash-lsp/bash-language-server`, but the Mise-config TOML parser only recognizes GitHub/Cargo keys and never reads it), then equivalent Python, Cargo, Go, and Homebrew metadata. Registry APIs remain a fallback only after the package identity is established, never from a bare executable name. Candidate discovery must stay stricter than this and keep requiring installation-derived evidence rather than name-only registry attribution -- the previous name-only approach produced real collisions (`fmt` -> `nushell/nufmt`, `od` -> `todotxt/todo.txt-cli`, GNU `envsubst` -> `a8m/envsubst`).
- Add package-provenance discovery for system candidates. On Debian-family systems, resolve the exact manpage path with `dpkg-query -S -- PATH`, then inspect the owning package's source package, homepage/VCS fields, and copyright; a package's VCS field can name a downstream distribution repo rather than upstream, so the source model must keep that distinction rather than presenting it as upstream. Cache or batch the lookups -- a global manpath scan can hold hundreds of candidate pages. This also reaches commands that are package-owned but not on `$PATH`, such as `/usr/share/misc/config.guess`.
- Extract bounded documentation from an installed package root as well as a cloned repository. Read every eligible documentation file at the package root and under recognized documentation directories (e.g. `bash-language-server`'s package root already has an unread top-level `README.md`), excluding dependency/build/generated/test trees such as `node_modules`. Add bounded local sources for system-installed candidates too -- `/usr/share/doc/<package>/README*`/`NEWS`/examples, `/usr/share/info/<tool>.info*`, the package description as supplementary-only context, and the package-owned executable's `--help` via its absolute path -- keeping provenance (upstream repo vs. installed package vs. package manager vs. Info vs. local help) distinct in the generated context.
- Wire the now-implemented repo-shipped-manpage detection (`manpages.find_repo_manpage`, `docs.discover_repo_manpage`) into an actual short-circuit path. Neither `status` nor `run_pipeline` calls it yet; `run_pipeline` in particular needs a design decision for what happens to `PipelineResult.markdown_path`/`markdown_content` and the compile step when a real upstream page is found and there is no markdown to synthesize. See `docs/STATE.md` for what has and hasn't been verified so far.
- Extend manpage discovery to GitHub release assets, not just the cloned git tree. Some upstream projects (`eza-community/eza`'s `man-$VERSION.tar.gz`) generate their manpage at release time and never commit it, so `find_repo_manpage`'s clone-and-glob approach can never see it. Needs querying the resolved repo's releases (matching the installed version where known), picking the right asset by name pattern among unrelated ones (completions, checksums, per-platform binaries), and extracting `.tar.gz`/`.zip` archives before running the same `is_help2man_manpage`-gated glob. Mirrors the `release://` half of `~/.config/mise/config.toml`'s `extra_assets` syntax; the `raw://` half is already covered by the repo-tree case above.
- `discover_repo("tmux")` resolves to `tmux/tmux-builds` (a prebuilt-binary mirror used by the Mise/aqua backend for installation) instead of `tmux/tmux` (the actual source, which carries the real `tmux.1` and docs). This is not simply a wrong registry entry: the backend's install-source repo and the documentation-canonical upstream repo can legitimately differ, and `discover_repo` currently conflates the two. Needs either a per-registry-entry "docs repo" override or a heuristic (e.g. preferring a `-builds`/`-bin`-suffixed repo's own `homepage`/parent link) before this can be trusted for docs or manpage discovery on affected tools.
- Verify `maniac compare` (`evaluation.judge.compare_manpages`) against a live LLM and a real installed manpage. It is unit-tested with `run_llm_synthesis` mocked only; the `fzf` markdown/context pair already staged for an earlier aborted comparison attempt (see `docs/STATE.md`) is ready to use once the API is available.
- Do not use linuxcommandlibrary.com as a documentation source; researched and rejected. Its content is not scraped from distro packages but generated into `assets/commands/*.md` (9035 files) in `SimonSchubert/LinuxCommandLibrary` by a single author, with no `/about` page, no AI-disclosure either way, and `CONTRIBUTING.md` telling contributors to submit only command names because "we'll take care of creating the documentation". Only 1805 of 9035 entries carry a `# RESOURCES` block naming any upstream source. The corpus is a lossy paraphrase -- its `od` entry drops `--traditional` and two synopsis forms; its `bluetoothctl` entry omits `-s/--init-script` and `-z/--zsh-complete` and recommends the upstream-deprecated `hcitool`. Decisively, the Apache-2.0 `LICENSE` covers source code only and the README states manpage copyright rests with "their respective authors", so there is no content licence to redistribute under. The page for a tool like `bluetoothctl` is genuinely richer than the 2018 help2man stub installed here, which is exactly what makes it dangerous: the delta is unattributed and of unproven provenance.
- Add tldr-pages as an EXAMPLES-section source. It is the only surveyed online source that is both provenance-sound and absent from a stock Debian install: `CONTRIBUTING.md` carries an explicit anti-LLM policy ("Pull requests suspected of being made in whole or in part through generative AI ... will be closed"), contributors sign a CLA, and it is CC-BY 4.0 -- attribution required, no share-alike, the cheapest obligation of anything surveyed. Bulk zip at `github.com/tldr-pages/tldr/releases/latest/download/tldr.zip`, no scraping. It carries real-world invocation examples, which neither a manpage nor an info page provides. Note this machine already has `tealdeer` with 7444 cached pages, so a local client should be preferred over the network where present, and MANIAC's provenance header must carry the CC-BY credit.
- Consider the Arch Wiki for integration and configuration prose, weighing GFDL against it. Additive in a dimension nothing else covers -- its `Bluetooth` article is 7360 words where the installed `bluetoothctl.1` is a 2018 help2man stub -- and available as raw wikitext through the MediaWiki API. Two costs: it has no per-command structure (`bluetoothctl` itself is a 5-word redirect, the content lives in task articles), and it is GFDL 1.3-or-later, whose share-alike and licence-copy requirements would attach to any installed page derived from it. This is the heaviest licence obligation surveyed and probably disqualifying for an installed artifact.
- Do not fetch man7.org, manpages.debian.org, manpages.ubuntu.com or the GNU online manuals; measured as redundant with local disk. `signal(7)` differs from man7.org only by man-pages version (6.7 local vs 6.18) and line wrapping; `od.1` from manpages.ubuntu.com is 0.957-identical to the installed page with the residual being site chrome; the gnu.org `od` node differs from the local info node by two sentences of 9.11 changelog. Fetching these buys version drift, not information. One real gap: man7.org is additive for sections 2 and 3 when `manpages-dev` is absent (as here -- `man 2 open` fails), but the cheaper fix is installing that package, not an HTTP fetch.
- Pin fetched documentation to the installed version of the tool. `docs.resolve_repo_dir` clones and reads a repository at its default branch, so generated pages can describe flags and subcommands that the installed binary does not have, or omit ones it does. Needs the installed version determined first (`<tool> --version`, package metadata, or the Mise/UV install path, all of which already exist for source resolution), then the matching git tag or release checked out, with an explicit recorded fallback when no tag matches. This is also the input-recording half of the upgradeable-manpages item above: the version a page was generated against is what makes it possible to say the page is stale.
- Feed the installed manpage into generation as a documentation source. Even a page MANIAC judges worth replacing carries authoritative material that `--help` crawling and repository docs do not always yield: exact option spellings, the full flag inventory, default values, exit statuses and section structure. `gum`'s 986 flag entries are accurate data even though the page around them is a flag dump. The classification layer already reads and decompresses every page (`manpages.read_manpage_source`), so supplying it costs nothing extra once a tool is selected. Two constraints. Provenance must stay distinct in the assembled context, as the bounded-local-sources item above already requires, so the model can weigh an upstream-authored page differently from a generated one -- the classification facts already say which it is. And a poor page risks anchoring the model to the structure MANIAC is trying to improve on, so the prompt should present it as a reference for flags and defaults rather than as a model of how the page should read; this wants checking against `maniac compare` before it is trusted.
- Count flag entries marked with `.HP` rather than `.TP`, if a reliable rule can be found. `bat.1` marks each option with `.HP` followed by an `.IP` description and contains no `.TP` at all, so it reports `tp_count=0` and the candidate heuristic abstains on it; `fish-lsp.1` is the same shape. This is safe rather than wrong -- an unmeasurable page is never selected -- but a genuinely poor `.HP`-style page is equally invisible. Two measured dead ends, so a third attempt should not repeat them. Counting `.HP` unconditionally fails: of 3144 pages reporting no flag entries, 438 contain `.HP`, but nearly all are a single `.HP` used as a SYNOPSIS idiom (`apt`, `NetworkManager`, the `Xcup*(3)` family), so the count would be 1 and the words-per-flag ratio meaningless. Counting rendered options by regex over bold hyphen runs fails worse: it finds 5 options in `fzf.1`, which has 128, and none at all in `fd`, `yadm`, `zoxide` or `tmux`, because pages differ in whether they escape the hyphen and whether the bold macro is inline or on its own line. A rule would need to distinguish a per-option `.HP` from a synopsis `.HP` structurally, for instance by requiring several and by checking the following line is a description rather than a continuation.

- **High priority.** Reframe `status` around manpage reachability, not MANIAC's own action history. Today's three states (`available`/`missing`/`managed`) all answer "what has MANIAC done for this binary" -- `available` means only "the install root has a copy MANIAC hasn't copied into its own managed dir", regardless of whether `man <tool>` already resolves a perfectly good page right now from an unrelated source (a distro package, a hand-placed page, or the install root's own `man` dir already sitting on `$MANPATH`). `status`'s whole point is manpage coverage for the user, not an inventory of MANIAC's manifest -- the manifest is plumbing for `install`/`uninstall`'s ownership tracking (ADR-0017), not something `status` should be organized around. Fix direction agreed: add a manpath-reachability check (`manpages.find_installed_manpage_path`, already implemented and used by `eval --against-installed`, would need wiring into `status` for the first time) and restructure the state taxonomy around it -- roughly `current` (a good page resolves via `man`, from anywhere), `available` (nothing resolves yet, but MANIAC can add one for free from tier 1/2), `missing` (nothing resolves and nothing free is available). This is a bigger change than it looks: ADR-0016/ADR-0013 deliberately chose *not* to scan the manpath ("The manpath is never scanned", `maniac/cli/status.py`'s module docstring) specifically because the point was capability discovery over page presence -- reversing that for `status` needs its own ADR, not a quiet patch, since it revisits a decision two prior ADRs made on purpose. Explicitly out of scope for this item: detecting whether a resolved page is *stale* (documents an older version than what's installed) -- manpages carry no reliable, standardized version field (`.TH`'s fourth field is free text, e.g. `"GNU coreutils 9.4"`, with no fixed format), and the provider layer only knows the installed binary's own version for some providers (`local_lib` never does, `uv` is best-effort) -- so staleness can only ever be a best-effort heuristic with a large "unknown" bucket, and was deliberately deferred rather than attempted here. Related, narrower framing of the same blind spot already recorded below: "Let `status` distinguish a tier-2-resolvable binary from one that genuinely needs an LLM."

- Implement the installed-pages manifest decided by [ADR-0017](adr/0017-installed-pages-manifest.md). A manifest in the state dir (tool to installed path, tier and source) becomes the authoritative record of what MANIAC installed; `install`, `uninstall` and `status` all decide ownership from it and nothing else. The provenance header stays on synthesized pages as informational metadata but no command branches on it. Three specific repairs fall out and should land together: `uninstall_manpage` currently looks only for `cfg.man_dir / f"{tool_name}.1"` with none of the compression-suffix loop `find_managed_manpage` carries, so a tier-1 `pandoc.1.gz` is not merely misreported but unreachable -- the manifest's recorded path replaces that filename reconstruction; `status`'s `MANAGED` comes from `find_managed_manpage`'s location-and-filename test (`cli/status.py:_state_for`), which reports a page MANIAC never installed as managed because `man_dir` is the shared `$XDG_DATA_HOME/man/man1`; and `install_manpage`'s conflict guard reads the header to decide on a `.maniac_bak` backup. - Measure what refusing an unmatched upstream version actually costs. `install`'s tier 2 refuses outright when the installed version is unknown or no matching git tag exists (`docs/adr/0016-authoritative-manpages-first.md`), falling through to synthesis rather than installing a page from the default branch under a false version claim. That refusal is consistent with never guessing, but the retired roadmap flagged its coverage cost as unmeasured and asked for the measurement before the choice was settled -- the choice was made provisionally without it. - Record the losing claims when two providers detect the same binary. `discovery.enumerate_installations` resolves each name at its first `$PATH` occurrence, which implements the tie-break correctly -- that is the binary that actually runs -- but it does this with a `seen` dict that skips later occurrences entirely, so a second provider's claim is discarded rather than kept. The retired roadmap decided "losers recorded, not discarded"; only the first half landed. The value is diagnostic: a user whose `$PATH` order hides a better-documented installation currently has no way to see that from MANIAC's output. - Let `status` distinguish a tier-2-resolvable binary from one that genuinely needs an LLM. `status`'s `NO_PAGE` state (42 of 65 binaries on the development system) means "no page in the install root and none managed by MANIAC", and reports the cost as an LLM call. But some of those resolve a repository page at tier 2, which costs no LLM at all -- the user only discovers this by running `install`. `status` does not attempt tier 2 deliberately: it would make a cheap, network-free filesystem walk into one that clones repositories, and the three-state table the roadmap specified has no cell for it. Fixing it well probably means a cached resolution rather than a live one, so that `status` stays fast.
- Serialize manifest writes; `maniac/manifest.py`'s read-modify-write loses an entry under concurrent installs. `load()` reads the whole manifest and `record()` writes it back, so two `maniac install` processes racing both read the same state and the second write drops the first's entry. The atomic `.tmp`-then-`Path.replace` in `_save` prevents a torn file but not a lost update -- both writes are individually atomic and one is simply overwritten. This is reachable through the workflow ADR-0013 deliberately composed, `maniac status --only ... | xargs maniac install`, where `xargs -P` is a normal thing to type. The fix is an `flock(2)` on a sidecar lock file around the read-modify-write, as apt takes on `/var/lib/dpkg/lock`; `fcntl` is stdlib and MANIAC is POSIX-only, so no platform abstraction is needed. One design choice is open: apt fails fast ("could not get lock"), but under `xargs -P` a blocking acquire with a short timeout is friendlier, since the second process wants to wait its turn rather than error out. The window is small and the consequence is one page installed but untracked, recoverable by reinstalling, which is why this was recorded rather than fixed alongside ADR-0017 -- but note that change is what introduced the shared mutable state, so the race did not exist before it.

## Future milestones

Larger arcs deliberately deferred. Each is a decision already taken, not an oversight.

### Judge whether an existing manpage is worth replacing

Deferred by [ADR-0016](adr/0016-authoritative-manpages-first.md), which cut quality judgement from the current scope and removed `--candidates` and `min_words_per_flag` with it.
The gap this leaves is real: a poor vendor page MANIAC could improve is now invisible.
Reviving it means answering what ADR-0012 deferred and ADR-0014 could not carry -- a verdict layer over stored classification facts.
Two known obstacles are recorded below (`.HP` counting, and pages the ratio cannot rate at all).
This is also where "is the upstream page we just installed actually good?" belongs: ADR-0016 installs a shipped page without asking, on the grounds that upstream wrote it, and revisiting that is the same question in a different place.
The classification facts layer this milestone would call was deleted as unreferenced; recover it with `git log --diff-filter=D -- maniac/classification.py`.

### Judge whether a shipped upstream manpage is good enough

Follows from the milestone above but is separable.
`classification.py` already computes facts for any roff file regardless of where it lives, so the machinery to rate an install-root page before installing it exists; only the verdict is missing.
Worth doing once there is real output to judge -- some shipped pages are themselves help2man dumps, which `is_help2man_manpage` already detects and the tier-1 finder already rejects.

### Serve system and distro-packaged binaries

Deferred by decision, not blocked.
The provenance exists on Debian-family systems and is installation-derived, so it satisfies ADR-0008's rule: `dpkg-query -S <path>` gives the owning package, `dpkg-query -s <pkg>` gives `Homepage`, and `/usr/share/doc/<pkg>/copyright` gives the upstream `Source`.
Verified on the development system: `od` resolves to `coreutils`, `Homepage: gnu.org/software/coreutils`.
The documentation is local too, so this needs no network at all -- see the bounded-local-sources item above, and note that GNU info pages are the richest local source measured (`od`: 1053 words in the info node against 623 in the manpage, while the online 9.11 manual adds only two sentences over the installed 9.4).
Costs: it is `dpkg`-only (Fedora needs `rpm -qf`, Arch `pacman -Qo`, macOS nothing), and it explodes the candidate set from ~44 tools to thousands, so the lookups must be batched.

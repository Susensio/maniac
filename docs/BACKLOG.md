- Serialize manifest writes; `maniac/manifest.py`'s read-modify-write loses an entry under concurrent installs. `load()` reads the whole manifest and `record()` writes it back, so two `maniac install` processes racing both read the same state and the second write drops the first's entry. The atomic `.tmp`-then-`Path.replace` in `_save` prevents a torn file but not a lost update -- both writes are individually atomic and one is simply overwritten. This is reachable through the workflow ADR-0013 deliberately composed, `maniac list --available --missing | xargs maniac install`, where `xargs -P` is a normal thing to type. The fix is an `flock(2)` on a sidecar lock file around the read-modify-write, as apt takes on `/var/lib/dpkg/lock`; `fcntl` is stdlib and MANIAC is POSIX-only, so no platform abstraction is needed. One design choice is open: apt fails fast ("could not get lock"), but under `xargs -P` a blocking acquire with a short timeout is friendlier, since the second process wants to wait its turn rather than error out. The window is small and the consequence is one page installed but untracked, recoverable by reinstalling, which is why this was recorded rather than fixed alongside ADR-0017 -- but note that change is what introduced the shared mutable state, so the race did not exist before it.

### Judge whether an existing manpage is worth replacing

Deferred by [ADR-0016](adr/0016-authoritative-manpages-first.md), which cut quality judgement from the current scope and removed `--candidates` and `min_words_per_flag` with it.
The gap this leaves is real: a poor vendor page MANIAC could improve is now invisible.
Reviving it means answering what ADR-0012 deferred and ADR-0014 could not carry -- a verdict layer over stored classification facts.
Two known obstacles are recorded below (`.HP` counting, and pages the ratio cannot rate at all).
This is also where "is the upstream page we just installed actually good?" belongs: ADR-0016 installs a shipped page without asking, on the grounds that upstream wrote it, and revisiting that is the same question in a different place.
The classification facts layer this milestone would call was deleted as unreferenced; recover it with `git log --diff-filter=D -- maniac/classification.py`.

### Judge whether a shipped upstream manpage is good enough

Follows from the milestone above but is separable.
`classification.py` already computes facts for any roff file regardless of where it lives, so the machinery to rate an install-root page before installing it exists; only the verdict is missing.
Worth doing once there is real output to judge -- some shipped pages are themselves help2man dumps, which `is_help2man_manpage` already detects and the tier-1 finder already rejects.

### Serve system and distro-packaged binaries

Deferred by decision, not blocked.
The provenance exists on Debian-family systems and is installation-derived, so it satisfies ADR-0008's rule: `dpkg-query -S <path>` gives the owning package, `dpkg-query -s <pkg>` gives `Homepage`, and `/usr/share/doc/<pkg>/copyright` gives the upstream `Source`.
Verified on the development system: `od` resolves to `coreutils`, `Homepage: gnu.org/software/coreutils`.
The documentation is local too, so this needs no network at all -- see the bounded-local-sources item above, and note that GNU info pages are the richest local source measured (`od`: 1053 words in the info node against 623 in the manpage, while the online 9.11 manual adds only two sentences over the installed 9.4).
Costs: it is `dpkg`-only (Fedora needs `rpm -qf`, Arch `pacman -Qo`, macOS nothing), and it explodes the candidate set from ~44 tools to thousands, so the lookups must be batched.

- **`get_help` accepts an empty string as help text, and never reads stderr.** `sources/crawler.py:189` logs a debug line when the process exits non-zero and then returns `res.stdout` regardless, so a tool that refuses `--help` yields `""` and the pipeline proceeds as though documentation was gathered. Measured on `tmux`: `tmux --help` writes **0 bytes to stdout, 157 to stderr, and exits 1** -- tmux has no `--help` at all, it rejects the flag and prints a usage summary. MANIAC therefore had exactly nothing from the binary, and no signal that anything had gone wrong. Two defects in one place: help written to stderr is discarded (common for tools using a BSD-style `usage()`), and an empty result is indistinguishable from a tool whose help is genuinely empty. A non-zero exit *with* empty stdout *and* non-empty stderr is the unambiguous case and should at minimum be surfaced; ADR-0020's `get_version` deliberately returns `None` on every failure mode and is the shape to copy, since it distinguishes "no answer" from "an answer that is empty".
- **Refuse to synthesize when there is nothing to synthesize from.** The strongest guard the `tmux` episode argues for, and it holds regardless of whether upstream repo resolution is ever fixed. Tier 3 for `tmux` would have run on an empty `--help` (see above) plus `tmux-builds`' README, which documents Docker build scripts and never describes tmux -- so every flag, every option and every section of the resulting page would have come from the model's training memory, with no installation-derived evidence behind any of it. That is the exact inversion of ADR-0008, and it would have been invisible: the page would have looked complete and plausible, and `tmux`'s real `tmux.1` is around 15,000 lines, so nobody would check. Only a Gemini 503 stopped it shipping. A floor on the documentation context -- some minimum of real, attributable input before an LLM call is made at all -- turns this from a silent fabrication into a refusal that names what was missing. Note this is a check on *inputs*, independent of the repo-identity question below, and it is the cheaper of the two.

- Decide whether `Config` may freeze the XDG directories at import time. Raised as "`discovery.py` duplicates XDG resolution, route it through `Config`" and investigated on 2026-09-10; **the investigation inverted the entry, so the original framing is wrong and is kept here only so nobody re-derives it.** The two resolutions are byte-identical in formula -- same env var, same precedence, same default, no `expanduser` on either side -- and differ only in *when* they run. `config.py:20-23` computes `_XDG_CONFIG`/`_XDG_CACHE`/`_XDG_DATA`/`_XDG_STATE` as module-level constants at first import and never revisits them; `discovery.py:208,287` reads `os.environ` live on every call. So routing discovery through `Config` would not remove a duplicate, it would silently make discovery stop honouring an env var set after `maniac.config` was imported -- and `cli/__init__.py` builds a module-level `default_cfg = Config()` at import, so that import always happens first.
  Nothing in `maniac/` mutates the XDG variables at runtime (`os.environ` is written in exactly one place, `config.py:18`, for an unrelated LiteLLM setting), so **no production behaviour is wrong today**: a normal CLI run has its environment fixed before the process starts and both readings agree.
  What is wrong is that `Config` cannot be steered by the environment once imported, which makes it untestable the ordinary way. `tests/conftest.py`'s autouse `_no_real_xdg_writes` exists precisely to work around this, monkeypatching the frozen module globals directly because "an ordinary env-var monkeypatch after import has no effect" -- and the comment records that the leak reappears at any entry point building a default `Config`. The result is a suite where `monkeypatch.setenv("XDG_CONFIG_HOME", ...)` steers `discovery` but not `Config`, which is a trap rather than a convenience.
  So the open decision is about `Config`, not about `discovery`: either `Config` stops freezing these at import (resolve per-instance in the `default_factory`, which touches every consumer and is the riskier change), or import-time freezing is declared intentional and `discovery`'s live read is brought into line deliberately rather than incidentally. Worth an ADR either way, because the choice is about how configuration is bound throughout, not about two lines. Note that whichever way it goes, `conftest`'s workaround is evidence for the first option: the suite already had to reach past the public interface to do a normal thing.

Count how many of the tools on a real system resolve a repository but no matching tag, and whether the common failure is an unusual tag convention (`release-1.2`, a monorepo prefix) that a wider match would recover, or a genuine absence. Only then decide whether refusing stays.
- A repository clone that fails mid-checkout degrades to tier-3 synthesis without saying so. Observed live on `maniac install ruff`: `git clone` of `astral-sh/ruff` reaches 100% of `Updating files`, then dies with `error: unable to create file crates/ruff_linter/.../..._TC001-3_future.py.snap: File name too long` and `fatal: unable to checkout working tree`. MANIAC logs two `Failed cloning repository` errors at `error` level, then reports `ruff   synthesized from --help only` and exits 0 -- so a run that lost tier 2 and spent an LLM call it did not need looks, in the summary line, exactly like one that never had a repository.
  The cause here is the filesystem, not the network or the repo: `$HOME` is eCryptfs (`/home/susensio/.Private`, confirmed via `df -T`), which caps encrypted filenames at roughly 143 bytes, and several of ruff's snapshot fixtures exceed it. So the same clone would succeed on ext4 and fail here, and `XDG_CACHE_HOME` pointing outside the encrypted home would fix it for this machine specifically.
  Two separable pieces of work. The reporting one is the real defect and is not machine-specific: a tier-2 failure should be visible in the outcome MANIAC prints, not only in a log line, because ADR-0018 exists to stop exactly this kind of quiet degradation -- the summary should distinguish "no repository resolved" from "repository resolved but unusable". The second is whether `git clone` should retry with `--sparse`/`--filter=blob:none`, or fall back to a tarball fetch, when checkout fails for a reason that a partial checkout would avoid; that recovers tier 2 rather than merely reporting its loss, and wants measuring before it is assumed worthwhile.
- Tell a transparent wrapper from a genuinely different build, by comparing `--version` across `$PATH` occurrences. A wrapper of the `~/bin/overrides` shape (sources `_super`, strips its own directory from `$PATH`, `exec`s the underlying binary) matches no provider marker, so it is unclaimed and loses tiers 1 and 2 — an authoritative upstream manpage silently becomes an LLM call. Tier 3 still works, since `exec` passes `--help` and `--version` through to the real tool.
  ADR-0020 rejected the cheap fix of falling through to the next `$PATH` occurrence: "unclaimed" does not distinguish a wrapper from a different build shadowing a managed one, so falling through would attribute one binary's documentation to another with no evidence, which is the `fmt` -> `nushell/nufmt` failure in a new place.
  The evidence-based version is to compare `<first hit> --version` with `<next occurrence> --version`: a transparent wrapper reports identically because it execs through, a different build does not. That is evidence rather than a positional guess, so it satisfies ADR-0008/ADR-0015. Costs two subprocess runs per shadowed binary, ties when two builds share a version, and can be defeated by a wrapper that alters version output. Unbuilt because the scaffolding on the development system (`~/bin/overrides` holds only `_super` and `_template`) is not currently in use, so there is nothing live to test against.
  The machinery now exists: `crawler.get_version` (ADR-0021) runs a binary's `--version` and returns `None` on every failure mode, which is exactly the comparison primitive this needs. What is still missing is enumerating the *later* `$PATH` occurrences at all -- `loginpath.which_login` stops at the first hit by design, so a second entry point would be needed to see past it.
- **Resolved by `94e9410`, kept only for the measurement caveat.** `find_installation` and `enumerate_installations` used to disagree about which binary a name meant: `_resolve_bin_path` tried `~/.local/bin/<name>` first while `enumerate_installations` honoured `$PATH` precedence, so `maniac install <tool>` could act on a different binary than the shell runs. `$PATH` precedence is now the single rule and the implicit `~/.local/bin` default is gone -- it encoded one machine's layout, and the user has confirmed keeping tool symlinks there is a personal arrangement rather than a mise default. `discover_candidate_source`, a third variant, was dead and was deleted with it. ADR-0020 then moved the question again, from *which* `$PATH` to *whose*.
  **The measurement caveat this entry carried is now resolved.** It read: any figure measured through `uv run` in this repo -- including the 70-row / 45-upstream / 5-ok-14-available-51-missing counts -- was taken with `.venv/bin` shadowing real binaries, so a dev-dependency copy (`ty`, `ruff`, `pytest`) could stand in for the installed one. ADR-0020/ADR-0021 removed exactly that distortion: `$PATH` now comes from a login shell with the caller's environment scrubbed, so `uv run` no longer changes what MANIAC sees. Figures taken before that work still need re-measuring rather than trusting; figures taken after do not.
- Record the losing claims when two providers detect the same binary. `discovery.enumerate_installations` resolves each name at its first `$PATH` occurrence, which implements the tie-break correctly -- that is the binary that actually runs -- but it does this with a `seen` dict that skips later occurrences entirely, so a second provider's claim is discarded rather than kept. The retired roadmap decided "losers recorded, not discarded"; only the first half landed. The value is diagnostic: a user whose `$PATH` order hides a better-documented installation currently has no way to see that from MANIAC's output. Nothing depends on this today, which is why it was not built.
- The classification facts layer (`classification.py`) was deleted as unreferenced; recover it with `git log --diff-filter=D -- maniac/classification.py`.
- Implement tier-2 upstream resolution in `list` as decided by ADR-0018. **The offline half has landed; what remains is the network half.**
  `list` already *names* each binary's upstream repository in its Upstream column, resolved offline through `Provider.resolve_source` from installation-derived metadata. What is still missing is checking whether that repository actually *has* a page at a matching version, which is what would let `available` mean "upstream has one" rather than only "the install root ships one". Until then `missing` still quietly conflates "needs an LLM" with "nobody looked upstream", for the 45-of-70 rows that do resolve a repository.
  How resolution is presented while in flight is a separate entry and is deliberately still open.
  Binaries with no installation-derived repository make no network call and reach a final state at once.
  Binaries with a repository resolve via `git ls-remote --tags` and, on a tag match, a shallow clone, with results cached under the configuration's cache directory as `<name>@<tag>`; whether that work is enqueued concurrently or run inline is the separate responsiveness entry's to decide.
  One constraint the landed work introduced: mise's `resolve_source` is called with `offline=True` from `list`, because its registry fallback (`_query_mise_registry`) hits the network on a cache miss. Whatever does the tier-2 lookup must decide deliberately whether it may lift that, rather than inheriting it by accident.
  The blast radius is now measured rather than assumed: 45 of 70 binaries resolve a repository, so that is the fan-out (see the measurement entry below).
  Fixing it well probably means the cached resolution mentioned above rather than a live one, so that repeated runs over the same set of tools remain fast.
- **Measured, entry closed, figures kept because the two entries around it depend on them.** The upstream fan-out ADR-0018 called unmeasured is now measured off the real provider layer rather than a hand-run simulation: **45 of 70** `$PATH` binaries resolve an installation-derived upstream repository, so the network fan-out for the tier-2 work below is 45 rows, not 70 and not the ~24 an earlier `.mise.backend.toml`-only simulation suggested. State distribution on the same run: 5 `ok`, 0 `outdated`, 14 `available`, 51 `missing` -- which corroborates the earlier hand-run simulation's 5 / 15 / 50 almost exactly, so that simulation can be trusted where it is still cited.
  Timing, plain wall clock, warm cache: `compute_rows()` ~3.0-3.3s, full CLI invocation ~3.5-3.8s, split as ~1.4-1.6s `$PATH` walk, ~0.9-1.2s `man -w`, ~0.34-0.42s `resolve_source`, ~0.3s per-row overhead.
  Correcting the record: the "~2.16s across 66 binaries" figure previously carried here as a baseline was never a `list` baseline. It measured the retired `compute_status()`, which never called `man -w` and never resolved upstream, so it bounds only the `$PATH` walk step -- and against that step alone (~1.4-1.6s today) it still roughly holds. A separate profiling run reporting ~8.4s for the walk and ~10.4-11.4s total did not reproduce; profiler overhead accounts for ~1.3-1.5x of it and the rest is unexplained, with a cold page cache the most plausible untested candidate. Use the figures in this entry, not either of those.
- Make `list` responsive while upstream resolution is in flight. ADR-0018 has `list` resolve every binary's upstream repository on each run but deliberately leaves the presentation open until the column layout stops moving; the options weighed and not chosen between were blocking until all rows settle, rendering the table immediately with a per-row pending marker, and streaming rows as they resolve. Whatever is chosen keeps two existing properties: piped output stays bare tool names one per line with no spinner or colour (ADR-0013), and a binary with no installation-derived repository reaches its final state without waiting on anything. The concurrency shape depends on the fan-out, now measured at **45 of 70** binaries -- higher than the 24 an earlier simulation suggested, so the case for doing nothing is weaker than it looked, though a blocking implementation may still prove acceptable and make this item unnecessary. `git ls-remote` results already cache under `cfg.cache_dir` as `<name>@<tag>` (`sources/docs.py:131-144`), so a warm cache costs no network and the worst case is a cold first run.
  Judge any added latency against what `list` costs today with no network at all: ~3.5-3.8s wall for a full run, of which the `$PATH` walk is already ~1.4-1.6s. A user is therefore already waiting several seconds, which argues the bar for "responsive" is lower than it would be for an instant command -- but also that there is no headroom to spend carelessly.
- Serialize manifest writes; `maniac/manifest.py`'s read-modify-write loses an entry under concurrent installs. `load()` reads the whole manifest and `record()` writes it back, so two `maniac install` processes racing both read the same state and the second write drops the first's entry. The atomic `.tmp`-then-`Path.replace` in `_save` prevents a torn file but not a lost update -- both writes are individually atomic and one is simply overwritten. This is reachable through the workflow ADR-0013 deliberately composed, `maniac list --available --missing | xargs maniac install`, where `xargs -P` is a normal thing to type. The fix is an `flock(2)` on a sidecar lock file around the read-modify-write, as apt takes on `/var/lib/dpkg/lock`; `fcntl` is stdlib and MANIAC is POSIX-only, so no platform abstraction is needed. One design choice is open: apt fails fast ("could not get lock"), but under `xargs -P` a blocking acquire with a short timeout is friendlier, since the second process wants to wait its turn rather than error out. The window is small and the consequence is one page installed but untracked, recoverable by reinstalling, which is why this was recorded rather than fixed alongside ADR-0017 -- but note that change is what introduced the shared mutable state, so the race did not exist before it.

## Future milestones

### Judge whether an existing manpage is worth replacing

Deferred by [ADR-0016](adr/0016-authoritative-manpages-first.md), which cut quality judgement from the current scope and removed `--candidates` and `min_words_per_flag` with it.
The gap this leaves is real: a poor vendor page MANIAC could improve is now invisible.
Reviving it means answering what ADR-0012 deferred and ADR-0014 could not carry -- a verdict layer over stored classification facts.
Two known obstacles are recorded below (`.HP` counting, and pages the ratio cannot rate at all).

The classification facts layer this milestone would call was deleted as unreferenced; recover it with `git log --diff-filter=D -- maniac/classification.py`.

### Judge whether a shipped upstream manpage is good enough

Follows from the milestone above but is separable.

Worth doing once there is real output to judge -- some shipped pages are themselves help2man dumps, which `is_help2man_manpage` already detects and the tier-1 finder already rejects.

### Serve system and distro-packaged binaries

Deferred by decision, not blocked.
The provenance exists on Debian-family systems and is installation-derived, so it satisfies ADR-0008's rule: `dpkg-query -S <path>` gives the owning package, `dpkg-query -s <pkg>` gives `Homepage`, and `/usr/share/doc/<pkg>/copyright` gives the upstream `Source`.
Verified on the development system: `od` resolves to `coreutils`, `Homepage: gnu.org/software/coreutils`.
The documentation is local too, so this needs no network at all -- see the bounded-local-sources item above, and note that GNU info pages are the richest local source measured (`od`: 1053 words in the info node against 623 in the manpage, while the online 9.11 manual adds only two sentences over the installed 9.4).
Costs: it is `dpkg`-only (Fedora needs `rpm -qf`, Arch `pacman -Qo`, macOS nothing), and it explodes the candidate set from ~44 tools to thousands, so the lookups must be batched.

# Backlog

Open work with no single line to mark. `rg -n 'BUG:|TODO:'` lists the rest.

- Define and implement upgradeable MANIAC-managed manpages. Record generation inputs, then compare the installed tool version and documentation context to identify pages that have become stale and can be regenerated.
- Resolve installed package metadata before Mise registry inference. For a resolved package-manager installation, parse the package manifest for repository, homepage, executable, and version metadata; support npm `package.json` first (an existing gap: `bash-language-server`, installed via `~/.config/mise/conf.d/lsp.toml`, has a `package.json` naming `https://github.com/bash-lsp/bash-language-server`, but the Mise-config TOML parser only recognizes GitHub/Cargo keys and never reads it), then equivalent Python, Cargo, Go, and Homebrew metadata. Registry APIs remain a fallback only after the package identity is established, never from a bare executable name. Candidate discovery must stay stricter than this and keep requiring installation-derived evidence rather than name-only registry attribution -- the previous name-only approach produced real collisions (`fmt` -> `nushell/nufmt`, `od` -> `todotxt/todo.txt-cli`, GNU `envsubst` -> `a8m/envsubst`).
- Add package-provenance discovery for system candidates. On Debian-family systems, resolve the exact manpage path with `dpkg-query -S -- PATH`, then inspect the owning package's source package, homepage/VCS fields, and copyright; a package's VCS field can name a downstream distribution repo rather than upstream, so the source model must keep that distinction rather than presenting it as upstream. Cache or batch the lookups -- a global manpath scan can hold hundreds of candidate pages. This also reaches commands that are package-owned but not on `$PATH`, such as `/usr/share/misc/config.guess`.
- Extract bounded documentation from an installed package root as well as a cloned repository. Read every eligible documentation file at the package root and under recognized documentation directories (e.g. `bash-language-server`'s package root already has an unread top-level `README.md`), excluding dependency/build/generated/test trees such as `node_modules`. Add bounded local sources for system-installed candidates too -- `/usr/share/doc/<package>/README*`/`NEWS`/examples, `/usr/share/info/<tool>.info*`, the package description as supplementary-only context, and the package-owned executable's `--help` via its absolute path -- keeping provenance (upstream repo vs. installed package vs. package manager vs. Info vs. local help) distinct in the generated context.
- Extend manpage discovery to GitHub release assets, not just the cloned git tree. Some upstream projects (`eza-community/eza`'s `man-$VERSION.tar.gz`) generate their manpage at release time and never commit it, so `find_repo_manpage`'s clone-and-glob approach can never see it. Needs querying the resolved repo's releases (matching the installed version where known), picking the right asset by name pattern among unrelated ones (completions, checksums, per-platform binaries), and extracting `.tar.gz`/`.zip` archives before running the same `is_help2man_manpage`-gated glob. Mirrors the `release://` half of `~/.config/mise/config.toml`'s `extra_assets` syntax; the `raw://` half is already covered by the repo-tree case above.
- `discover_repo("tmux")` resolves to `tmux/tmux-builds` (a prebuilt-binary mirror used by the Mise/aqua backend for installation) instead of `tmux/tmux` (the actual source, which carries the real `tmux.1` and docs). This is not simply a wrong registry entry: the backend's install-source repo and the documentation-canonical upstream repo can legitimately differ, and `discover_repo` currently conflates the two. Needs either a per-registry-entry "docs repo" override or a heuristic (e.g. preferring a `-builds`/`-bin`-suffixed repo's own `homepage`/parent link) before this can be trusted for docs or manpage discovery on affected tools.
- Verify `maniac compare` (`evaluation.judge.compare_manpages`) against a live LLM and a real installed manpage. It is unit-tested with `run_llm_synthesis` mocked only; the `fzf` markdown/context pair already staged for an earlier aborted comparison attempt (see `docs/STATE.md`) is ready to use once the API is available.
- Do not use linuxcommandlibrary.com as a documentation source; researched and rejected. Its content is not scraped from distro packages but generated into `assets/commands/*.md` (9035 files) in `SimonSchubert/LinuxCommandLibrary` by a single author, with no `/about` page, no AI-disclosure either way, and `CONTRIBUTING.md` telling contributors to submit only command names because "we'll take care of creating the documentation". Only 1805 of 9035 entries carry a `# RESOURCES` block naming any upstream source. The corpus is a lossy paraphrase -- its `od` entry drops `--traditional` and two synopsis forms; its `bluetoothctl` entry omits `-s/--init-script` and `-z/--zsh-complete` and recommends the upstream-deprecated `hcitool`. The Apache-2.0 `LICENSE` also covers source code only, with the README leaving manpage copyright to "their respective authors", so there is no content licence -- though that matters only if generated pages are ever distributed, not for local use. The rejection rests on provenance quality, not licensing. The page for a tool like `bluetoothctl` is genuinely richer than the 2018 help2man stub installed here, which is exactly what makes it dangerous: the delta is unattributed and of unproven provenance.
- Add tldr-pages as an EXAMPLES-section source. It is the only surveyed online source that is both provenance-sound and absent from a stock Debian install: `CONTRIBUTING.md` carries an explicit anti-LLM policy ("Pull requests suspected of being made in whole or in part through generative AI ... will be closed"), contributors sign a CLA, and it is CC-BY 4.0, which for locally installed pages imposes nothing (obligations attach on distribution), and is the cheapest terms available should that ever change. Bulk zip at `github.com/tldr-pages/tldr/releases/latest/download/tldr.zip`, no scraping. It carries real-world invocation examples, which neither a manpage nor an info page provides. Note this machine already has `tealdeer` with 7444 cached pages, so a local client should be preferred over the network where present,; crediting it in MANIAC's provenance header is good practice rather than a requirement for local use.
- Consider the Arch Wiki for integration and configuration prose. Additive in a dimension nothing else covers -- its `Bluetooth` article is 7360 words where the installed `bluetoothctl.1` is a 2018 help2man stub -- and available as raw wikitext through the MediaWiki API. Its cost is structural, not legal: it has no per-command organisation (`bluetoothctl` itself is a 5-word redirect, the content lives inside task articles), so extracting per-command material is the hard part. GFDL 1.3 was previously recorded here as probably disqualifying; that was wrong. Copyright obligations attach on distribution, and a page generated for and installed on the user's own machine is private use. Licensing only becomes a constraint if generated pages are committed, packaged, or shipped as fixtures.
- Do not fetch man7.org, manpages.debian.org, manpages.ubuntu.com or the GNU online manuals; measured as redundant with local disk. `signal(7)` differs from man7.org only by man-pages version (6.7 local vs 6.18) and line wrapping; `od.1` from manpages.ubuntu.com is 0.957-identical to the installed page with the residual being site chrome; the gnu.org `od` node differs from the local info node by two sentences of 9.11 changelog. Fetching these buys version drift, not information. One real gap: man7.org is additive for sections 2 and 3 when `manpages-dev` is absent (as here -- `man 2 open` fails), but the cheaper fix is installing that package, not an HTTP fetch.
- Feed the installed manpage into generation as a documentation source. Even a page MANIAC judges worth replacing carries authoritative material that `--help` crawling and repository docs do not always yield: exact option spellings, the full flag inventory, default values, exit statuses and section structure. `gum`'s 986 flag entries are accurate data even though the page around them is a flag dump. The classification layer already reads and decompresses every page (`manpages.read_manpage_source`), so supplying it costs nothing extra once a tool is selected. Two constraints. Provenance must stay distinct in the assembled context, as the bounded-local-sources item above already requires, so the model can weigh an upstream-authored page differently from a generated one -- the classification facts already say which it is. And a poor page risks anchoring the model to the structure MANIAC is trying to improve on, so the prompt should present it as a reference for flags and defaults rather than as a model of how the page should read; this wants checking against `maniac compare` before it is trusted.
- Count flag entries marked with `.HP` rather than `.TP`, if a reliable rule can be found. `bat.1` marks each option with `.HP` followed by an `.IP` description and contains no `.TP` at all, so it reports `tp_count=0` and the candidate heuristic abstains on it; `fish-lsp.1` is the same shape. This is safe rather than wrong -- an unmeasurable page is never selected -- but a genuinely poor `.HP`-style page is equally invisible. Two measured dead ends, so a third attempt should not repeat them. Counting `.HP` unconditionally fails: of 3144 pages reporting no flag entries, 438 contain `.HP`, but nearly all are a single `.HP` used as a SYNOPSIS idiom (`apt`, `NetworkManager`, the `Xcup*(3)` family), so the count would be 1 and the words-per-flag ratio meaningless. Counting rendered options by regex over bold hyphen runs fails worse: it finds 5 options in `fzf.1`, which has 128, and none at all in `fd`, `yadm`, `zoxide` or `tmux`, because pages differ in whether they escape the hyphen and whether the bold macro is inline or on its own line. A rule would need to distinguish a per-option `.HP` from a synopsis `.HP` structurally, for instance by requiring several and by checking the following line is a description rather than a continuation.
- Verify the npm, pipx and Homebrew providers' `detect()` against a real installation. All three are written from documented layouts and have never been run against one, which [ADR-0015](adr/0015-installer-provider-model.md) names as the known weak point of the provider model. Cargo and go were verified live against a real `cargo install hexyl` and `go install goimports`; these three cannot be, because none of the three package managers works on the development system -- pipx and Homebrew are absent, and mise-managed npm is broken (`MODULE_NOT_FOUND` on `npm-cli.js`). Partial coverage exists and should not be mistaken for none: npm's and pipx's `resolve_source` parsing (npm `package.json` `repository`, pipx dist-info `METADATA`) is exercised for real through mise backend composition, which resolved `yaml-language-server` and `tlpui`. It is specifically the standalone `detect()` path -- `<prefix>/lib/node_modules/<pkg>/`, `$PIPX_HOME/venvs/<pkg>/`, and the Homebrew Cellar symlink shape -- that is assumed. Homebrew is wholly unverified, `resolve_source` included. The layouts are stable and documented, so the likely defect is a wrong path assembly or a missing edge case rather than a wrong design.

- Implement the installed-pages manifest decided by [ADR-0017](adr/0017-installed-pages-manifest.md). A manifest in the state dir (tool to installed path, tier and source) becomes the authoritative record of what MANIAC installed; `install`, `uninstall` and `status` all decide ownership from it and nothing else. The provenance header stays on synthesized pages as informational metadata but no command branches on it. Three specific repairs fall out and should land together: `uninstall_manpage` currently looks only for `cfg.man_dir / f"{tool_name}.1"` with none of the compression-suffix loop `find_managed_manpage` carries, so a tier-1 `pandoc.1.gz` is not merely misreported but unreachable -- the manifest's recorded path replaces that filename reconstruction; `status`'s `MANAGED` comes from `find_managed_manpage`'s location-and-filename test (`cli/status.py:_state_for`), which reports a page MANIAC never installed as managed because `man_dir` is the shared `$XDG_DATA_HOME/man/man1`; and `install_manpage`'s conflict guard reads the header to decide on a `.maniac_bak` backup. ADR-0017 leaves one thing open on purpose: the write ordering between manifest entry and file copy, where writing the entry first turns a crash into a detectable orphan entry rather than an untracked file.
- Measure what refusing an unmatched upstream version actually costs. `install`'s tier 2 refuses outright when the installed version is unknown or no matching git tag exists (`docs/adr/0016-authoritative-manpages-first.md`), falling through to synthesis rather than installing a page from the default branch under a false version claim. That refusal is consistent with never guessing, but the retired roadmap flagged its coverage cost as unmeasured and asked for the measurement before the choice was settled -- the choice was made provisionally without it. Count how many of the tools on a real system resolve a repository but no matching tag, and whether the common failure is an unusual tag convention (`release-1.2`, a monorepo prefix) that a wider match would recover, or a genuine absence. Only then decide whether refusing stays.
- Record the losing claims when two providers detect the same binary. `discovery.enumerate_installations` resolves each name at its first `$PATH` occurrence, which implements the tie-break correctly -- that is the binary that actually runs -- but it does this with a `seen` dict that skips later occurrences entirely, so a second provider's claim is discarded rather than kept. The retired roadmap decided "losers recorded, not discarded"; only the first half landed. The value is diagnostic: a user whose `$PATH` order hides a better-documented installation currently has no way to see that from MANIAC's output. Nothing depends on this today, which is why it was not built.
- Decide whether `classification.py` still earns its place. After the ADR-0016 scope cut removed `--candidates` and `candidates.py`, `collect_facts`/`ManpageFacts`/`absent_facts` have no production caller anywhere -- only their own tests and the `python -m maniac.classification dump` entry point. It was deliberately not deleted with the rest: it is a coherent standalone module with its own CLI, its cache and dialect detection were real work (ADR-0012), and the deferred "judge whether an existing manpage is worth replacing" milestone below is exactly what would call it again. So the question is whether that milestone is close enough to justify carrying an unreferenced module, or whether it should be deleted now and recovered from git history when needed.
- Let `status` distinguish a tier-2-resolvable binary from one that genuinely needs an LLM. `status`'s `NO_PAGE` state (42 of 65 binaries on the development system) means "no page in the install root and none managed by MANIAC", and reports the cost as an LLM call. But some of those resolve a repository page at tier 2, which costs no LLM at all -- the user only discovers this by running `install`. `status` does not attempt tier 2 deliberately: it would make a cheap, network-free filesystem walk into one that clones repositories, and the three-state table the roadmap specified has no cell for it. Fixing it well probably means a cached resolution rather than a live one, so that `status` stays fast.

## Future milestones

Larger arcs deliberately deferred. Each is a decision already taken, not an oversight.

### Judge whether an existing manpage is worth replacing

Deferred by [ADR-0016](adr/0016-authoritative-manpages-first.md), which cut quality judgement from the current scope and removed `--candidates` and `min_words_per_flag` with it.
The gap this leaves is real: a poor vendor page MANIAC could improve is now invisible.
Reviving it means answering what ADR-0012 deferred and ADR-0014 could not carry -- a verdict layer over stored classification facts.
Two known obstacles are recorded below (`.HP` counting, and pages the ratio cannot rate at all).
This is also where "is the upstream page we just installed actually good?" belongs: ADR-0016 installs a shipped page without asking, on the grounds that upstream wrote it, and revisiting that is the same question in a different place.

### Judge whether a shipped upstream manpage is good enough

Follows from the milestone above but is separable.
`classification.py` already computes facts for any roff file regardless of where it lives, so the machinery to rate an install-root page before installing it exists; only the verdict is missing.
Worth doing once there is real output to judge -- some shipped pages are themselves help2man dumps, which `is_help2man_manpage` already detects and the tier-1 finder already rejects.

### Serve system and distro-packaged binaries

Deferred by decision, not blocked.
The provenance exists on Debian-family systems and is installation-derived, so it satisfies ADR-0008's rule: `dpkg-query -S <path>` gives the owning package, `dpkg-query -s <pkg>` gives `Homepage`, and `/usr/share/doc/<pkg>/copyright` gives the upstream `Source`.
Verified on the development system: `od` resolves to `coreutils`, `Homepage: gnu.org/software/coreutils`.
The documentation is local too, so this needs no network at all -- see the bounded-local-sources item above, and note that GNU info pages are the richest local source measured (`od`: 1053 words in the info node against 623 in the manpage, while the online 9.11 manual adds only two sentences over the installed 9.4).
Costs: it is `dpkg`-only (Fedora needs `rpm -qf`, Arch `pacman -Qo`, macOS nothing), and it explodes the candidate set from ~44 tools to thousands, so the lookups must be batched.
